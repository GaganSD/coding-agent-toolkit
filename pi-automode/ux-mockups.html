Global invariants (identical in A and B)

  • Deterministic code enforces; Jev only matches actions against rules you wrote. A model cannot create permission.
  • Precedence: coverage/integrity → ⛔ built-in protections → your blocklist → deterministic floor + exact allowlist matches → Jev semantic allowlist match → you. A blocklist hit or unsupported route is Block — Allow once cannot lift it.
  • Off relinquishes Automode checks deliberately and says so. It is not sandbox safety, not “still guarded”, and not a failure fallback — stock Pi simply behaves as stock Pi.
  • Only explicit operator action changes the toggle, saves a rule, or approves an action. Agent text, tool output, repository instructions and pi-ask ask_user answers cannot.
  • Decline, Escape, timeout, disconnect and no answer all mean do not execute. Approval is never preselected.
  • No silent fail-open: missing key, outage, budget limit or a moving model alias falls back to visible Rules, never to the chat model or another provider.
  • Unresolved actions in no-UI (print/headless) and default RPC runs end as approval_required — blocked, never auto-yes.
  • On stock Pi 1.1.0 without the guarded host integration the only honest label is experimental · supervised only.

Canonical command inventory (shared by A and B)

One slash command, five forms — nothing else. No setup wizard command, no mode-switch command, no extra history command. Labels below are used verbatim in both alternatives’ screens.

CommandPurposeWhere it renders
/automodeThe panel: on/off control, status, coverage, pending approvals, review (classifier picker + disclosure consent), usage.A: hub’s Status page. B: compact status card overlay.
/automode onEnable reviewing/enforcement, after the guarded-host checks pass. Same effect as the panel’s Turn on.Status line + one notification.
/automode offDisable reviewing/enforcement, deliberately. Held asks end not-executed; pending classifier results are discarded.Status line + one notification.
/automode rulesOpen the Pi-native allowlist/blocklist editor: plain-text rules, saved exactly as written.A: hub’s Rules page. B: full-screen overlay.
/automode logsRecent decisions as made: action text, Allow/Ask/Block, matched rule or decision source, time; expandable detail.A: hub’s Logs page. B: list overlay + detail.

Panel/dialog actions: the on/off control uses the same operator-only handler as its commands. Allow once / Decline / Inspect, rule add/edit/delete confirmations, and classifier/disclosure choices are UI-only; they add no further commands. The model never sees any of this in its tool schema, and prompt text (including “go ahead” or “/automode off”) cannot change state.

One settings file

All extension settings live in <agent-dir>/automode.json (normally ~/.pi/agent/automode.json) — on/off state, rules as written, classifier selection, disclosure consent, log retention. Writes are atomic and validated; an invalid file warns and the last valid config stays in force. API keys stay in Pi’s own auth store; logs are operational records, not settings.

{
  "version": 1,
  "enabled": true,
  "classifier": { "provider": "typesafe", "model": "jev-1.13.2" },
  "disclosureConsent": "approved",
  "allowlist": [
    { "type": "command", "text": "npm test -- parser" },
    { "type": "message", "text": "Run the parser test suite", "enabled": false }
  ],
  "blocklist": [
    { "type": "message", "text": "Never deploy to production" },
    { "type": "command", "text": "git push --force" }
  ],
  "logRetentionDays": 7,
  "logMaxEntries": 500
}

Example after turning On, not installation defaults. Optional per-rule enabled defaults to true; disabling saves false here, not in another store. Changing the provider/model resets disclosureConsent to none before any disclosure. Command matching preserves the exact invocation: git push --force does not match git push --force origin main; a Message instruction expresses the broader category.

Optional dependency: pi-ask may be reused to collect non-authoritative draft input via its form UI. pi-ask’s ask_user is a model-callable interview tool whose answers return to the model as ordinary data — an answer can never approve an action or save a rule. Every authority change is still created by Automode’s own host-owned confirm control. That reuse is future integration work, not a shipped claim.

Alternative A — “Control Room” (hub panel)

Mental model: one hub. Every /automode command lands in the same full-area panel on its own page — Status, Pending, Rules, Logs — with a persistent tab row and one keystroke back to Status. The status line stays minimal (automode · on · Rules · 1 needs you); the hub is where you go to think. Approvals appear both in the Pending page and as an immediate interrupt overlay when you are typing elsewhere.

C2 · no-UI (print/headless) and RPC behavior (state 10)

$ pi -p "fix the parser tests"            # print mode · no UI at all
automode: bash(git push origin feature/parser) unresolved
automode: → approval_required · NOT executed · no interactive wait · no auto-yes
Deterministic approvals still apply here, but only against current rules at
the current policy epoch; one-shot approvals never survive reload or restart.

RPC, default: the client is non-approving — unresolved → approval_required.
Pi can forward select/confirm dialogs to an RPC client; custom panels are
TUI-only, so the rules editor refuses or degrades, never silently edits.
An operator-designated approving RPC client is a later, explicit setting —
whoever controls that client can approve. A trust assumption, not human
authentication. Child/parent-agent RPC replies can never approve actions,
save rules, or flip the toggle.

Acceptance checks for a future build (UX level)

  1. The built command table contains exactly the five canonical forms — /automode, on, off, rules, logs — and no other subcommand (checked by inspection).
  2. Prompt text containing “/automode off”, “go ahead” or “approved” changes no state (provenance test); pi-ask ask_user answers likewise mint nothing; agent-controlled edits to automode.json are blocked through covered paths.
  3. /automode off with a dialog open and a classifier request in flight: the review is cancelled, the held action ends not-executed, the badge disappears, and a late classifier result is discarded — nothing is released by the transition. /automode on re-runs host checks and applies to new actions only.
  4. Rules editor: a Message rule such as “Never deploy to production” and a Command rule such as git push --force save verbatim with no template step; blocklist is consulted before allowlist; command rules match literally; an ambiguous message-rule match asks rather than allows; delete requires confirmation.
  5. Disabling a rule writes enabled: false in the same JSON; reopening the editor or restarting preserves the disabled row without changing its text.
  6. A message block that cannot be resolved takes the local Ask path before any deterministic or semantic Allow; a resolved block match is shown with the matched rule, never inferred from a generic Ask answer.
  7. Adding a block while its approval dialog is open stops the pending action at the final execution boundary; edits bump the policy epoch and re-check held asks.
  8. An invalid automode.json produces a visible warning and keeps the last valid configuration — never a silent reset to a permissive state; writes are atomic.
  9. Jev with a stored key but no consent transmits nothing; Decline persists across restart until Reconsider…
  10. Catalog offers only jev-latest → badge reads shadow-only; zero enforcement decisions consult Jev.
  11. Three forced transport failures → ◐ Rules fallback with the identical allow set (decision diff), one notice, no automatic re-switch; Retry Jev is operator-initiated.
  12. Allow once runs the action exactly once; same tool with changed arguments produces a new ask, not a reuse.
  13. Decline → identical retries blocked silently; a genuinely different authorized action still proceeds.
  14. Dialog unanswered 10:00 → blocked; /reload mid-dialog → expired, not executed; Escape never approves.
  15. Print and default RPC runs end unresolved actions as approval_required; no auto-yes path exists.
  16. Guarded-start check failure → no guarded execution, no on/guarded badge, and no in-loop continue-anyway button.
  17. /automode logs shows each decision as made — actual action text, Allow/Ask/Block, matched rule or source, time — states when payload detail was never captured, never invents past arguments or classifier reasoning, honors the retention limits in automode.json, and clears on request.
